## R01 — 영구 저장 후 취소 처리의 일관성 누락

위치: [TemporalSpatialMemoryService.swift:270–278](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/Perception/TemporalSpatialMemoryService.swift#L270-L278), [같은 파일:292–295](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/Perception/TemporalSpatialMemoryService.swift#L292-L295).

`journalRepository.append`는 동기 파일 commit을 끝낸 뒤 반환한다. 그런데 호출자가 재개되기 전에 작업이 취소되면 `validateGeneration` 내부의 `Task.checkCancellation()`이 캐시 갱신보다 먼저 예외를 던진다. 디스크 저널은 N, 메모리 coordinator는 N-1인 상태가 되고 `projectionPending`에도 표시되지 않는다.

`recover`는 캐시가 있고 pending 표시가 없으면 저널을 다시 읽지 않고 캐시를 반환한다(124–135줄). 다음 관측은 오래된 N-1을 이전 상태로 제출하므로 저널의 N과 불일치하여 `journalDiverged`가 발생한다. 단순히 다음 프레임을 처리하는 것으로 복구되지 않는다. 앱 비활성화 등에서 인식 작업은 취소하지만 해당 서비스 캐시는 유지하는 경로가 있어 정상 생명주기에서도 이 상태에 들어갈 수 있다.

또한 저널과 캐시는 갱신됐지만 metadata·관계 projection 중 취소된 경우, catch의 `validateGeneration`이 `projectionPending.insert`보다 먼저 취소를 다시 던진다. 이 경우에도 다음 `recover`가 미완료 projection을 재시도하지 않는다. 두 경로 모두 저널 자체가 삭제된다는 뜻은 아니며, 명시적 서비스 reset 또는 재시작을 통한 복구와 일반 다음 관측의 복구 동작이 다르다는 문제다.

수정 방향: 영구 commit 이후에는 작업 취소와 별도로 캐시·복구 필요 상태를 일관되게 반영하거나 저널에서 재구성해야 한다. 실제 `resetGeneration` 변경은 별도로 검사하여 삭제된 장소를 이전 작업이 되살리지 않도록 유지해야 한다.

회귀 검증: append의 영구 commit 직후 반환을 차단하고 취소하는 경우, metadata·관계 projection 중 취소하는 경우를 각각 제어 가능한 gate로 시험한다. 이어지는 새 관측이 정상 저장되고 디스크 저널·캐시·파생 데이터가 일치해야 한다. 기존 서비스 취소 테스트의 시작 전 취소만으로는 이 두 시점을 검증하지 못한다.

증거 수준: 두 검토자가 독립적으로 확인한 제어 흐름 결함. 이번 검토에서 새 Swift 회귀 테스트를 실행한 것은 아니다.

## R02 — 평가한 가구 방향과 표시 방향 불일치

위치: [CameraSurfaceView.swift:150–153](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/Camera/CameraSurfaceView.swift#L150-L153), [FurniturePlacementEvaluation.swift:1372–1374](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Packages/VispaceCore/Sources/VispaceCore/FurniturePlacementEvaluation.swift#L1372-L1374).

Core의 XZ 평면 사각형은 양의 yaw에서 X축을 +Z 방향으로 회전시킨다. 미리보기는 같은 yaw를 +Y축 quaternion에 그대로 넣어 X축을 -Z 방향으로 회전시킨다. 따라서 직사각형 가구가 45도일 때 두 footprint가 서로 다른 방향을 차지한다. 0도·90도 또는 정사각형만 확인하면 이 불일치를 놓칠 수 있다.

수치 확인: 중심이 원점이고 폭 2m·깊이 0.9m인 소파를 yaw 45도로 두었다. 장애물 영역 `x=0.55…0.65, z=-0.65…-0.55`의 네 꼭짓점은 모두 렌더링 footprint 안에 있지만, 평가 footprint의 깊이 경계와는 최소 약 0.328m 떨어져 있다. 평가가 통과하더라도 초록색 미리보기는 장애물과 겹칠 수 있다.

수정 방향: 평가와 RealityKit 표현에서 회전 규약을 통일하고, 변환을 공유하거나 명시적으로 검증한다.

회귀 검증: 폭과 깊이가 다른 가구에서 ±45도 등을 포함해 평가 footprint의 네 꼭짓점과 렌더링 변환 결과를 비교한다. 실제 장애물이 한쪽 footprint에만 들어가는 경우도 포함한다.

증거 수준: 소스 대조 및 Python으로 quaternion 회전과 평면 회전의 수치 대조를 수행했다. RealityKit 화면 또는 실기기 충돌 시험을 새로 실행한 것은 아니다.

## R03 — 배치 증거의 시간 경과와 개별 anchor 관측 시각 누락

위치: [FurniturePlacementController.swift:149–155](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/FurniturePlacement/FurniturePlacementController.swift#L149-L155), [같은 파일:587–593](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/FurniturePlacement/FurniturePlacementController.swift#L587-L593), [ARFurniturePlacementEvidenceBuilder.swift:245–247](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/FurniturePlacement/ARFurniturePlacementEvidenceBuilder.swift#L245-L247).

같은 세션·지도·좌표계·추적 상태에서 pose 시각만 진행되면 controller는 기존 배치 결과를 무효화하지 않는다. 평가 시작 시의 표면 나이는 기본 60초 이내여야 하지만, 공개한 결과가 그 이후에도 이 조건을 만족하는지 확인하는 유효기간 처리가 없다. 비동기 평가의 최종 게시 검사도 증거의 나이를 다시 검증하지 않는다.

증거 builder는 전체 surface snapshot의 timestamp만 검사하고 개별 plane·mesh의 `anchorObservedAt`을 확인하지 않는다. 오래된 바닥 anchor를 유지한 상태에서 무관한 anchor 갱신으로 snapshot 시각만 최신이 되면 오래된 바닥이 다시 최신 증거처럼 통과할 수 있다.

수정 방향: 사용한 anchor 각각의 관측 시각을 검증하고, 결과를 게시하는 시점에도 나이를 재확인한다. 게시 이후에는 표면 갱신 이벤트가 없어도 기한이 지나면 적합 표시와 미리보기를 철회해야 한다.

회귀 검증: 표면 갱신 없이 pose만 60초 이상 진행하는 경우, 계산 완료 전에 증거가 만료되는 경우, 무관한 anchor만 갱신해 오래된 바닥 anchor가 남는 경우를 각각 확인한다. 세션·지도 변경 시험은 이 세 경우를 대체하지 못한다.

증거 수준: controller와 evidence builder의 제어 흐름 및 시간 검사 대조. 새 Xcode 실행 또는 실제 방 시험은 하지 않았다.

## R04 — 새 물체의 연속 관측이 영구 상태 갱신으로 이어지지 않음

위치: [SpatialPerceptionController.swift:877–881](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/Perception/SpatialPerceptionController.swift#L877-L881).

새 물체를 승격하여 `.genuinelyNew`로 저장한 이후, 같은 promotion ID의 관측은 metadata 조회와 실제 재식별 검사에 도달하기 전에 반환된다. 관측 중에는 promoter의 `lastObservedAt`이 계속 갱신되어 후보가 만료되지 않으므로, 계속 보이는 새 물체는 처음 저장한 위치·마지막 관측 시각에 머물 수 있다. 이동한 새 물체에 대한 시간 정보도 갱신되지 않는다.

기존 40프레임 연속 재식별 시험은 물체가 영구 저장소에 이미 있는 상태에서 시작한다. 새 물체를 처음 발견하고 같은 관측 흐름을 계속 유지하는 위 경로를 검증하지 못한다.

수정 방향: 새로 저장한 물체도 다음 관측에서 실제 재식별 증거를 평가할 수 있게 한다. 단순 track 연속성만으로 `confirmedExisting`을 만들어서는 안 된다. 재식별 후보 builder가 입력과 같은 ID를 제외하므로 조기 반환만 제거하는 수정도 충분하지 않다. 입력 관측의 식별자와 저장된 영구 식별자를 구분해 계약을 정리해야 한다.

회귀 검증: 기존 물체가 없는 상태에서 유효 관측으로 새 물체를 승격·저장하고, 같은 관측 흐름을 40프레임 이상 지속하며 위치를 바꾼다. 영구 ID 중복 생성 없이 시각·위치가 갱신되는지, 동일성 증거가 부족하면 확정하지 않는지 함께 검사한다.

증거 수준: promoter 수명과 재식별 경로의 소스 대조. 이 신규 시나리오를 Swift 테스트로 실행한 것은 아니다.

## R05 — 파생 관계의 크기가 허용 입력 및 복구 계약과 맞지 않음

위치: [SpatialSceneGraphService.swift:165–208](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/SceneGraph/SpatialSceneGraphService.swift#L165-L208), [SceneGraphRepository.swift:398–407](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/Persistence/SceneGraphRepository.swift#L398-L407).

관계 서비스는 자격을 충족하는 물체 쌍마다 양방향 관계를 파생하며 전체 관계 수를 제한하지 않는다. 저장소는 전체 graph catalog JSON을 4MiB로 제한한다. 시간 기억과 장소 가져오기는 물체 2,048개까지 허용하므로 유효한 입력도 파생 저장 한도를 쉽게 초과한다.

예를 들어 서로 가까운 확정 물체 256개는 `near` 관계만으로 `256 × 255 = 65,280`개의 방향 있는 관계를 만든다. 관계마다 두 UUID의 텍스트 72바이트만 계산해도 4,700,160바이트로 4,194,304바이트 한도를 넘는다. JSON 구조·관계 ID·다른 predicate까지 포함하면 크기는 더 커진다.

가져온 metadata에는 이 규모의 물체가 들어갈 수 있지만, 저널이 없는 최초 복구에서 파생 그래프 저장이 실패한다. 관측 중 한도를 넘은 경우에도 projection 재시도가 같은 초과 상태를 계속 만들며 후속 관측 전에 실패할 수 있다. 파생 데이터 하나의 용량 초과가 원본 관측의 추가 처리를 막는 구조다.

수정 방향: 근접 관계를 제한하거나 필요한 관계만 파생·저장하도록 하며, 파생 cache의 용량 문제가 원본 관측과 복구 전체를 막지 않도록 분리한다. 입력 승인 한도와 실제 저장 가능한 데이터 규모의 관계도 검증해야 한다.

회귀 검증: 허용 범위의 밀집 물체를 가져온 뒤 복원하고 새 관측을 추가한다. 관계 축소·재생성 및 부분 projection 실패 뒤의 후속 처리도 확인한다. 단순 지도 개수 제한과 작은 graph 시험으로는 부족하다.

증거 수준: 생성·직렬화·복구 경로 대조와 관계 수·최소 크기 계산. Swift 대량 데이터 실행을 새로 수행한 것은 아니다.

## R06 — 개인정보 선언에서 사용 API 범주 누락

위치: [PrivacyInfo.xcprivacy:11–29](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/Resources/PrivacyInfo.xcprivacy#L11-L29), [SpatialStorageDirectory.swift:164–210](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/Persistence/SpatialStorageDirectory.swift#L164-L210), [VispaceServices.swift:318–319](https://github.com/L3J-Vispace/Vispace/blob/248c15f937b0e50671db6d5413462b0f0118f71d/Vispace/VispaceServices.swift#L318-L319).

현재 선언은 UserDefaults와 SystemBootTime 두 범주뿐이다. 그러나 저장 승인과 저장 공간 화면에서 `.systemFreeSize`를 읽으며, 보관 파일 정리에서 `.contentModificationDateKey`와 `.contentModificationDate`를 읽는다. 관측된 사용에 대응하는 DiskSpace와 FileTimestamp 범주가 빠져 있다.

Apple의 [required-reason API 범주와 허용 사유 문서](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype)에서 이 API 및 범주를 확인했다. 실제 사용 목적에 맞는 사유를 각각 선언해야 한다. 이는 개인정보 선언의 완전성 문제이며 실제 App Store 제출 실패나 원격 공격 성공을 확인했다는 뜻은 아니다.

현재 CI의 privacy plist 검사는 문법 유효성 중심이므로, 파일이 올바른 plist라는 사실만으로 소스의 API 사용을 모두 선언했는지 알 수 없다. 무서명 archive 성공도 이 누락을 해소하지 않는다.

수정 방향: 공간 측정의 쓰기 승인·사용자 표시 목적과 앱 컨테이너 파일 시각 사용에 맞는 Apple 허용 사유를 추가하고, source와 manifest 범주를 대조하는 검사를 보완한다.

회귀 검증: manifest를 파싱하여 소스에서 사용하는 required-reason 범주가 모두 포함되는지 확인하고, 최종 배포 archive의 개인정보 보고서에서도 선언을 확인한다.

증거 수준: plist 파싱 및 소스 호출 대조를 실행했고 Apple 공식 문서를 확인했다. App Store 업로드 검증은 실행하지 않았다.
